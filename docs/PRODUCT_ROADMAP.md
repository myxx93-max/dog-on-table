# 产品形态与功能规划

## 产品原则

一个数据底座，多种独立前端。个人开发者可以只做其中一种形态，不需要一次性开发 Web、App、小程序和短视频矩阵。

## 1. Web：最适合第一个版本

MVP 功能：
- 餐饮主体搜索：名称、地址、城市、统一社会信用代码（仅在合法公开且必要时使用）。
- 门店详情：主体信息、地址、来源记录、更新时间。
- 事件时间线：抽检、处罚、检查公示、风险提示等，按类型与时间展示。
- 原始出处：官方页面链接、发布机构、文号（如有）、发布日期。
- 证据标签：官方发布、媒体报道、用户反馈、待核实。
- 纠错入口：同名误匹配、信息过期、内容错误、主体已变更。
- 官方举报指引：跳转至官方平台或公开办事入口。

## 2. 微信小程序

适合：
- 快速搜索、扫码进入门店页。
- 收藏关注门店和接收用户主动订阅的更新提醒。
- 查看官方信息摘要与原始链接。
- 举报材料准备清单、官方渠道跳转。
- 用户反馈和纠错。

需单独核验微信平台类目、备案、隐私政策、用户信息处理、订阅消息和内容审核要求。不要假设网站功能可直接复制到小程序。

## 3. App

适合在需求被验证后再开发：
- 多门店收藏和更新订阅。
- 地图附近查询（仅展示来源明确的信息）。
- 本地缓存公开资料和用户自行保存的材料。
- 用户反馈进度（仅当项目确实有能力处理时）。
- 无障碍与长辈友好展示。

早期不建议为了“看起来完整”而同时开发 iOS 和 Android。

## 4. 抖音图文 / 短视频 / 公众号

内容栏目建议：
- 一条监管公告看懂：用通俗语言解释原始公告。
- 食品安全知识：冷藏、交叉污染、过期食品、餐饮卫生等。
- 消费者办事指南：如何保留消费凭证、如何通过官方渠道反映问题。
- 城市公开数据观察：统计口径、覆盖范围和时间窗口明确。
- 产品使用演示：展示如何查来源、看时间线和纠错。

内容规范：
- 不使用未经证实的“黑店”“毒餐厅”等定性标题。
- 不通过猎奇、羞辱、网暴制造流量。
- 不曝光消费者、员工或经营者个人隐私。
- 图文必须标明数据时间、来源和检索方式。
- 更正时同步更新原内容，保留更正记录。

## 5. 举报与反馈体验

建议采用“官方渠道助手”，而不是“自动举报器”：
1. 用户选择问题类型。
2. 展示当地市场监管部门或国家官方投诉举报入口。
3. 提示用户准备消费凭证、时间、地点、问题描述和相关照片等材料。
4. AI 可协助整理用户自己的事实陈述，不补造细节。
5. 用户逐项审阅，确认后自行跳转并提交。
6. 产品记录的是用户本地操作状态，不宣称已受理或已立案，除非有官方回执可核验。

## 6. 建议迭代

- V0：单城、单数据源、只读查询。
- V1：多源归档、主体消歧、时间线和纠错。
- V2：官方举报导航、材料整理和本地保存。
- V3：小程序与内容入口。
- V4：多城市扩展、企业合规工具和 API。

每一阶段以真实用户行为和数据质量决定是否进入下一阶段。
